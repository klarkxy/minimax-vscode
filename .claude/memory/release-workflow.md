# Repository Memory

## release workflow

- The repo uses `googleapis/release-please-action@v4` with `skip-github-pull-request: true` (temporary workaround for missing repo-level PR permission). When the manifest and CHANGELOG/package.json are already in sync, release-please is a no-op (`release_created: false`, `publish` job `skipped` in ~1s). When they are out of sync, release-please creates/pushes a release commit + tag + GitHub Release on its own.
- **As of 2.3.1, `release.yml` is fully automated for both auto and manual cuts.** The workflow triggers on `push: branches: [main]` *and* `push: tags: ['v*']`; the `publish` job fires on either `release_created == 'true'` (auto cut, on main push) or `startsWith(ref, 'refs/tags/v')` (manual cut, on tag push). It now does `vsce publish` → `ovsx publish` → `softprops/action-gh-release` in one shot. Required repo secrets: `VSCE_PAT` (VS Code Marketplace PAT) and `OVSX_PAT` (Open VSX PAT). Auto cuts double-fire (once on main push, once on the release-please-pushed tag), but `vsce publish --skip-duplicate` + the re-attach step are no-ops the second time, so it's safe.
- **Manual release-please cut pattern** (last used for v2.1.9, v2.3.0, v2.3.1):
  1. Commit `chore(release): <version> — <title>` with body explaining it's a manual cut. Include all the version-bump edits: `package.json#version`, `.github/release-please-manifest.json`, `CHANGELOG.md` / `CHANGELOG.zh.md` (prepend new section), and any non-version code changes (`.vscodeignore` hardening, workflow fixes, etc.).
  2. Push to `main` — release-please runs but produces nothing because everything is already aligned.
  3. `git tag -a v<version> -F <notes-file> <release-commit-sha>` with the CHANGELOG section as tag message.
  4. `git push origin v<version>` — this triggers `release.yml` automatically; the publish job builds, publishes to VS Code Marketplace + Open VSX, and attaches the VSIX to the GitHub Release. **Do not** run `gh release create` or `vsce publish` locally — the workflow handles it.
  5. Watch the Actions tab; if `vsce publish` fails, fix the underlying issue and re-push the same tag (or use `rescue.yml` to retry just the publish step without re-tagging).
- The `rescue.yml` workflow is the **escape hatch** for re-publishing an existing tag without cutting a new version (e.g. you tagged v2.3.1 but the marketplace publish step flaked on a network blip). It takes a `tag_name` input and optional `publish_vscode_marketplace` / `publish_open_vsx` / `attach_github_release` booleans. Use it when the auto workflow is broken mid-publish and you need a retry path.
- `package-lock.json` and `package.json` should both be bumped in the same commit as the version bump; release-please does not re-bump them when cutting manually. `git grep '"version"' package-lock.json` should match `package.json` before tagging.
- Release title format: `<version> — <subtitle>` (single em dash, space-padded). Examples: `2.3.0 — Drop custom commit pipeline, route Copilot's utility models`.
- The `dist/` directory is gitignored (`dist/`, `*.vsix`). Locally produced `.vsix` files from prior runs persist in `dist/` — clean with `rm -rf dist && npm run package` before attaching to a new release to avoid attaching a stale vsix from an earlier version.
- **Before tagging, sanity-check the bundle** to catch Marketplace validation issues locally before they cost a rejection + re-publish round-trip: `npm run package && npx vsce ls --no-dependencies | grep -iE '^(extension/)?(nul|con|prn|aux|com[1-9]|lpt[1-9]|\.claude|\.learnings)' && echo "REJECT" || echo "OK"`. The 0-byte `nul` leak that rejected v2.3.0 would have been caught by this.
